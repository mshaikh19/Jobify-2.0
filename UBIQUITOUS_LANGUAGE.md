## 2. Flagged Ambiguities

In accordance with DDD governance, every conceptual conflict identified in Jobify 2.0 has been cataloged and resolved below.

### Category A: Polysemy (One Word Means Two Different Things)

| Ambiguous Term | Meaning 1 | Meaning 2 | Conflict Analysis | Which One Wins |
| :--- | :--- | :--- | :--- | :--- |
| **Application** | The candidate's submission record to a specific job vacancy (`ApplicationResponse`). | The software program itself (FastAPI backend / React single-page app, `app = FastAPI()`). | Confusion arises when team members say "check the application" (referring either to software health or candidate submissions). | **"Application" strictly wins for the candidate's submission.** The software system must be designated as **"Platform"** or **"Jobify System"**. |
| **Status** | The lifecycle availability of a Job Posting (`active` vs `closed`). | The progress of a Candidate through hiring stages (`applied`, `interviewing`, `accepted`). | Leads to ambiguous API query parameters (`/jobs?status=...` vs `/applications?status=...`) and confusing database fields. | **Both terms are disambiguated.** The posting availability is **"Posting Status"**; candidate workflow progression is **"Pipeline Stage"**. The naked word *"Status"* is banned. |
| **Role** | The authentication and authorization persona of a user account (`JOB_SEEKER`, `EMPLOYER`, `ADMIN`). | The professional title or job discipline being hired for (e.g., "Full-Stack Developer", "Talent Lead"). | In conversation: "What role are you looking for?" can refer to account permissions or job title. | **"Job Title" wins for vacancies; "Account Persona" wins for auth permissions.** In domain models, reference the position as **"Job Title"** or **"Job Posting"**, and platform access as **"User Role"**. |
| **Pipeline** | The candidate progression funnel across recruitment stages (Applied &rarr; Reviewed &rarr; Interviewing &rarr; Accepted). | The automated CI/CD build, lint, and deployment pipeline for software releases. | DevOps discussions conflict with product recruitment features when discussing "pipeline status" or "broken pipeline". | **"Talent Pipeline" (or "Hiring Pipeline") wins** within the product domain. Software delivery automation must be explicitly designated as **"CI/CD Pipeline"**. |

### Category B: Synonymy (Two or More Words Mean One Thing)

| Competing Terms | Conflicting Usage in Code & UI | Semantic Resolution & Justification | Which One Wins |
| :--- | :--- | :--- | :--- |
| **Candidate** vs. **Job Seeker** vs. **Applicant** | The backend database and schemas use `UserRole.JOB_SEEKER` and `seeker_id`, design mockups use *"Candidate"*, while traditional recruitment features use *"Applicant"*. | A person seeking career advancement remains a "Candidate" throughout discovery, sourcing, and evaluation. "Applicant" only captures the passive moment of submitting, while "Job Seeker" sounds dated and transactional. | **"Candidate" wins.** All UI copy, API documentation, and future schema refactors must standardize on **Candidate** (with `candidate_id`). Legacy database field `seeker_id` is an internal alias mapping to Candidate. |
| **Recruiter** vs. **Employer** | The auth model uses `UserRole.EMPLOYER` and jobs have `employer_id`, while dashboard features, notes, and inquiries are labeled *"Recruiter"*. | "Employer" refers to the legal corporate entity (`company_name`), whereas "Recruiter" is the actual human actor posting jobs, reviewing resumes, and advancing candidates. | **"Recruiter" wins for the user actor; "Employer" wins for the company entity.** When speaking of the user taking action in the system, **Recruiter** wins. |
| **Job Posting** vs. **Job** vs. **Listing** vs. **Requisition** vs. **Vacancy** | The API uses `/jobs`, schemas say `JobCreate`, endpoint handlers say `my/postings`, and mockups use `requisitions` and `openings`. | "Job" is too abstract (can mean employment, a task, or a background process); "Requisition" is enterprise corporate jargon; "Listing" reduces an opening to a plain text advertisement. | **"Job Posting" wins.** In all product discussions, documentation, and user interfaces, the published vacancy entity is designated as a **"Job Posting"**. |
| **Saved Job** vs. **Bookmarked Job** vs. **Favorite** | Schema defines `SavedJobResponse` and route `/saved-jobs`, while UI components occasionally render bookmark icons or mention "favoriting a role". | Having multiple terms creates user confusion across web and mobile interfaces. | **"Saved Job" wins.** The action is "Save Job" and the repository is "Saved Jobs". "Bookmark" and "Favorite" are deprecated aliases. |
| **Resume** vs. **CV** | Endpoints use `/uploads/resume` and fields use `resume_url`, while British English or international candidates often refer to it as "CV". | Mixing "CV" and "Resume" causes fragmented naming in static assets, schema fields, and frontend labels. | **"Resume" wins.** Standardized across database attributes, API endpoints (`/uploads/resume`), and user interface file upload forms. |
| **Pipeline Stage** vs. **Application Status** | Schema defines `ApplicationStatus` (`applied`, `reviewed`, `interviewing`, `accepted`, `rejected`), while ATS views refer to Kanban stages. | "Status" implies a static Boolean or outcome, whereas candidate hiring is an active, progressive multi-stage journey. | **"Pipeline Stage" wins.** Represents the candidate's current stage in the hiring pipeline. |
